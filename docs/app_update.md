# 应用更新

应用内更新已加入开发版，尚未发布，记录于 [CHANGELOG 的 unstaged 条目](../CHANGELOG.md#unstaged)。1.3.1 及更早的版本没有此功能，需要先手动安装第一个包含它的版本，之后才能在应用内更新。

## 使用流程

1. 首页打开「设置」，在「应用更新」中查看当前版本，点击「检查更新」。
2. 应用从 GitHub Releases 读取最新的正式版本，与已安装的版本比较。没有更高的版本时，显示「已是最新版本」。
3. 发现新版本时弹出确认框，显示新版本号、当前版本和安装包大小；「查看更新说明」在浏览器中打开该版本的发布页。选择「暂不更新」关闭确认框，不下载任何内容；下次检查会再次询问。
4. 选择「更新」后开始下载安装包，显示已下载大小和进度，可以取消。
5. 下载并校验完成后，安装包交给 Android 的安装程序。首次更新时，系统会要求允许 Natsuko 安装应用，并显示自己的安装确认；允许之后，在应用内确认过的更新可以由系统直接安装。系统仍要求确认时，照常显示系统确认框。
6. 安装完成后 Natsuko 会关闭，需要重新打开。在系统确认框中取消，或在应用内点击「取消」，都不会改动已安装的版本。

检查、下载或安装失败时显示具体原因，例如无法连接 GitHub、访问次数受限、安装包校验失败、签名与已安装的应用不一致或存储空间不足，随后回到可以重新检查的状态。

## 行为规则

- **只在点击时联网。** 不在启动时、后台或定时检查更新；打开设置页也不会发起请求。重新进入设置页时不保留上一次的「已是最新版本」结果。
- **只提示更高的正式版本。** GitHub 的「最新 Release」不包含草稿和预发布版本。版本以 tag `v<主版本>.<次版本>.<修订号>` 与已安装的版本名逐段按数值比较（`1.10.0` 高于 `1.9.9`）；Debug 版本名的 `-debug` 后缀不参与比较。tag 不符合该格式时报告版本信息无法识别，不做猜测。
- **更新与文件处理互斥。** 安装更新会关闭应用，因此下载和安装期间不能开始新的导入或处理，分享导入会提示等待；处理或保存进行中时不能开始更新。检查更新本身不占用工作流。
- **更新状态独立于当前页面。** 确认框和进度框显示在所有页面之上，返回首页或重置工作流不会丢失；活动重建后继续显示。
- **安装包只保留一份。** 下载写入应用缓存目录 `update/`，开始下载时清除其他版本的旧文件。取消安装或在系统确认框中拒绝后，已通过校验的安装包保留，再次更新时直接使用，不重复下载；安装被系统拒绝时删除安装包。检查发现已是最新版本时清空该目录。

## 实现

代码位于 `data/update/`，界面状态与流程控制位于 `ui/AppUpdateController`、`ui/AppUpdateState` 和 `ui/AppUpdateUi`。更新状态不放入 `NatsukoUiState`：文件工作流在重置时会整体替换该状态。

- `ReleaseVersion`：解析并比较 `主.次.修订` 版本。
- `GitHubReleases`：解析 `https://api.github.com/repos/poppinzhang/Natsuko/releases/latest` 的响应。安装包优先取名为 `Natsuko-<版本>.apk` 的附件；没有时，如果该 Release 只有一个 `.apk` 附件则使用它，否则报告缺少安装包。已安装的旧版本无法得知后来的命名变化，这条回退规则保证附件改名后仍能更新。发布页地址由仓库名和已校验的 tag 拼出，不取自响应内容。
- `UpdateHttpClient`：受限的 HTTPS 传输。版本信息只访问 `api.github.com`；安装包只访问 `github.com` 及 `*.githubusercontent.com`（GitHub 的发布存储）。每次操作最多 5 个请求（含重定向），拒绝非 HTTPS、带用户信息或非默认端口的地址，重定向到其他域名时在连接前终止。连接与单次读取超时均为 15 秒；版本信息总时限 60 秒、响应上限 1 MiB；安装包总时限 30 分钟、大小上限 512 MiB。未认证请求不携带任何账号信息，只发送固定的 `User-Agent: Natsuko`。
- `GitHubAppUpdater`：下载到临时文件，字节数必须与 Release 公布的大小完全一致，并校验 GitHub 为附件提供的 SHA-256 摘要；不一致时删除文件并报告错误。GitHub 未提供摘要时只校验大小。
- `AppUpdateInstaller`：先读取安装包信息，包名必须与当前应用相同、内部版本号必须高于已安装版本，否则在出现任何系统提示之前报告原因。随后通过 `PackageInstaller` 会话安装，并用 `setAppPackageName` 限定只能覆盖本应用。**签名由 Android 校验**：安装包的签名与已安装的应用不一致时，系统拒绝安装。会话结果通过未导出的广播接收器返回；需要用户确认时，系统确认界面由前台界面打开。取消、失败和下次安装前都会放弃遗留的会话。

应用不执行下载的文件：安装包只交给系统安装程序，由系统替换整个应用。这与「不在运行时下载可执行文件、原生库或编解码器」的约束不冲突——视频和元数据组件仍然随包内置，本地功能不依赖任何下载。

更新使用两项权限：`REQUEST_INSTALL_PACKAGES`（请求安装应用，需用户在系统设置中允许）和 `UPDATE_PACKAGES_WITHOUT_USER_ACTION`（应用内已确认的自身更新可以不再弹出系统确认）。未引入新的依赖库。

## 发布要求

应用内更新依赖 [构建与发布流程](build_release.md) 中的 Release 约定，修改发布流程时需保持：

- tag 为 `v<版本号>`，Release 公开并标记为最新；
- 附件中有正式签名的 `Natsuko-<版本号>.apk`（或至少保证该 Release 只有一个 `.apk` 附件）；
- 使用与已发布版本相同的签名密钥，`VERSION_CODE` 高于所有已发布版本。

仓库地址变更时，更新 `GitHubReleases.REPOSITORY`；已安装的旧版本依靠 GitHub 对旧地址的重定向继续工作。

## 已知限制

- GitHub 对未认证的 API 请求按 IP 限制为每小时 60 次。共用出口 IP 的网络可能提前用尽额度，此时提示稍后重试。
- 需要能够访问 GitHub。应用不使用第三方镜像或加速服务。
- 安装完成后系统会结束应用进程，应用不会自动重新打开。
- 不支持断点续传；下载中断后需重新下载。
- Debug 构建的包名带 `.debug` 后缀，与正式安装包不是同一个应用：可以检查到新版本并下载，但会在安装前提示安装包与当前应用不匹配。
- 通过应用商店分发时需另行评估：例如 Google Play 不允许应用自行更新，并限制 `REQUEST_INSTALL_PACKAGES` 的使用。

## 验证

JVM 测试覆盖版本解析与比较；HTTPS 边界（域名、协议、端口、重定向次数与跨域重定向）、HTTP 状态与限流提示、大小不符或截断的下载、超时、取消时断开连接并清理文件；下载目录清理、已校验安装包的复用、摘要不符时删除，以及安装被拒绝、用户拒绝和取消后的文件保留规则；更新流程的状态转换、忙碌互斥、失败提示和取消。

Android 仪器测试覆盖 Release JSON 解析（安装包选择、摘要格式、无效响应、已是最新时清理缓存）、安装前对无效文件、其他应用的安装包和非更高版本的拒绝，以及设置页流程：当前版本显示、不点击不联网、已是最新、确认与拒绝、下载进度、更新期间拒绝导入、取消、失败提示和系统确认界面无法打开时的处理。界面测试使用脚本化的更新器，不访问 GitHub，也不安装任何应用。

实际安装会替换并结束被测应用，无法放入自动化测试。发布前在 Android 16 设备上手动验证：安装上一个正式版本，发布新版本后在设置中检查更新，确认首次的系统授权与安装确认、安装后版本号正确，并再次检查显示「已是最新版本」。
