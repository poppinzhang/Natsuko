# 架构与工作流

## 边界

应用采用单 Activity + Jetpack Compose。`NatsukoViewModel` 只负责工作流状态与调度，耗时操作统一在 `Dispatchers.IO` 上运行；处理器不依赖 UI，并通过回调报告进度。

- `ui/`：首页、设置、配置、推文链接输入、进度、结果与分享操作。
- `data/ShareImportParser`：解析 `ACTION_SEND`、`ACTION_SEND_MULTIPLE`、`ClipData` 和 `EXTRA_STREAM`，去重 URI。
- `data/DocumentResolver`：从 `ContentResolver` 获取文件名和 MIME 类型。
- `data/twitter/`：推文链接规范化、X 官方元数据解析与访问状态分类、本机加密登录态存储、HTTPS 流式下载与网络边界校验。
- `data/update/`：应用更新。GitHub Release 版本信息解析与版本比较、受限 HTTPS 下载与校验，以及通过系统 `PackageInstaller` 覆盖安装。
- `processing/`：图片/PDF/GIF 处理器、推特下载调度与可单测的布局、黑边检测和帧计划算法；图片调整的几何计算、单次重采样导出与试编码会话。
- `processing/video/FfmpegVideoEngine`：共用的视频处理入口，负责 FFprobe 元数据探测、FFmpeg 滤镜与编码流程；`FfmpegRunner` 管理原生进程、进度及取消。功能处理器负责 URI 暂存、任务目录和输出管理。当前和后续所有视频资源处理都复用此层。
- `data/OutputRepository`：创建每次运行的应用专属目录，生成 FileProvider URI；存储层管理持久输出设置，并将成品直接发布到默认 Download 目录或获授权的自定义目录下的功能子目录，不创建用户可见的运行时间戳目录。

## 外观设置

设置页提供「外观 → 颜色模式」，支持跟随系统（默认）、浅色（Light）和深色（Dark）。颜色偏好独立持久保存，共享 Compose 主题根据用户选择与当前系统模式确定全局配色，并保持系统栏图标对比度；切换立即生效，重新启动和分享导入沿用同一偏好。界面外观不参与图片、PDF 或视频处理，也不改变预览中的纸张与填充色。交互与验证要求见 [外观与颜色模式](appearance.md)。

## 主流程

界面文案通过 Android 语言资源解析；默认资源使用英文，简体中文、繁体中文、韩语和日文资源独立维护，后续功能同步维护全部五种语言。语言选择使用系统 `LocaleManager`，由 Android 保存并与系统应用语言设置同步。状态中的进度、错误及结果说明以资源标识和参数保留，在显示时根据当前配置解析，避免语言切换后残留旧文案。详见 [国际化与语言设置](i18n.md)。

1. 用户在首页选择功能，系统选择器只显示匹配类型；推特下载进入链接输入页。也可在其他应用的分享面板中选择一个 Natsuko 功能。
2. URI 经过去重、MIME/扩展名校验后进入对应流程。不匹配项被跳过，全部无效时显示错误。“去除黑边”在本地选择或分享导入后立即自动处理；“图片调整”进入单图编辑页，多张分享时先由用户选择其中一张；其余功能进入配置页。
3. 需要配置时，用户调整参数和顺序并开始处理；配置页保留在内存中。所有处理流程均显示进度并允许取消；去除黑边逐张处理，无需确认参数。
4. 批处理中单个文件失败不会丢弃其他文件的成功结果；结果页同时展示成功文件和逐文件错误。去除黑边全部成功时返回首页，保留成功提示和“查看结果”入口；开始新工作流或重置前可重新打开最新成品。存在处理或用户目录保存失败时，直接进入结果页查看逐文件错误。
5. 处理器先将输出写入应用专属目录。启用“保存至用户存储目录”时，随后自动保存到所设用户目录，结果页显示保存进度和实际保存位置；否则直接展示应用专属输出。
6. 开关关闭时，结果页在“保存位置”下方提供同一开关。开启即保存本次结果，并持久启用后续自动保存；保存失败按文件报告并保留应用专属副本，重试只处理尚未保存成功的文件。
7. 打开或分享使用对应结果的 `content://` URI，并给予接收应用临时只读授权；已保存结果使用用户目录 URI，应用专属结果使用 `FileProvider` URI。完整目录与授权规则见 [输出存储](output_storage.md)。

## 分享入口

Manifest 定义八个带独立名称与 MIME 过滤器的 `activity-alias`：图片拼接、去除黑边、图片转 PDF、PDF 转图片、视频转 GIF、下载推特视频（GIF）、图片调整、复制图片位置。入口组件名决定功能，URI 同时从 `ClipData` 和 extras 读取，以兼容不同发送方。`CropBlackBorderShare` 接收 `image/*` 的 `ACTION_SEND` 和 `ACTION_SEND_MULTIPLE`，支持单张截图和多图分享导入。

分享导入会自动进入所选功能的处理流程。“去除黑边”使用固定的保守检测规则，导入后直接开始自动处理；四项文件配置功能在正式处理前保留配置确认。`ImageAdjustmentShare` 接收单张或多张 `image/*`，进入同一编辑页，不触发自动处理；存在未导出编辑时，新的导入需先确认放弃。`DownloadTwitterVideoShare` 只接收 `text/plain` 的 `ACTION_SEND`，从 `EXTRA_TEXT` 与 `ClipData.text` 提取唯一推文链接，进入链接页后由用户点击下载，不解引用分享方提供的文件 URI。

## 图片调整

编辑页只保存几何参数和轻量撤销历史，预览使用最长边 2560 px 的 sRGB 解码。纯 Kotlin 的 `AdjustmentGeometry` 为预览、尺寸显示、试编码和导出计算同一个结果，并合成一个从源像素到成品的仿射变换。导出页在后台按当前格式和质量试编码到应用缓存，以完整文件的字节数显示预估大小；保存时提交同一份文件，再沿用输出存储层自动保存。细节见 [图片调整](image_adjustment.md)。

## 推特下载与 GIF 串联

下载器先向 X 自家公开 syndication 接口请求推文信息；信息不足时，从受限的官方推文网页或元数据响应中识别当前推文的结构化状态。必须匹配请求的推文编号，不从网页中的其他推文、普通登录按钮或不明确的 HTTP 错误推断登录限制。仅明确需要登录时，ViewModel 挂起下载并询问用户；同意后打开 X 官方登录页，取得登录态、加密保存并重试元数据请求。删除、作者限制可见、地域限制、限流及未知原因均直接报告对应错误。登录流程及账号访问权限的边界见 [下载推特视频](download_twitter_video.md)。此登录功能自 1.3.3 起提供。

下载页的「登录 X」是独立的用户主动入口，可用于在原因不明时尝试登录；它不改变自动错误分类规则。主动登录成功后回到输入页，保留链接，由用户点击开始下载；不会因为登录完成而自动发起下载。两种入口复用同一登录页、会话存储及清理逻辑。

`TwitterLoginDialog` 承载受限 WebView，先打开 X 官方公开入口，由用户点击网页上的登录入口；登录与验证由 X 页面处理；没有 JavaScript 原生桥，不保存密码。用户完成登录后，`TwitterSession` 仅保留元数据请求需要的 Cookie，既不写入 UI 保存状态，也不发送到视频 CDN。WebView 数据可能短暂写盘，因此打开与关闭时清理，并从云备份和设备迁移中排除；原生登录态通过 Android Keystore 的 AES-GCM 密钥加密，原子写入应用私有 `noBackupFilesDir`，不参与云备份或设备迁移。启动时异步恢复；每次账号操作或下载前重新读取持久记录并等待同步，以反映其他入口的清除或登录结果，避免下次下载复用旧内存会话。保存、读取和清除在后台执行，保存失败明确报错。ViewModel 结束只释放内存引用，不删除磁盘记录；用户主动清除或 X 明确报告认证失效时同时清除持久记录。普通 HTTP 401/403、网络错误和未知错误不使会话失效。此持久化行为及登录页修复自 [1.3.4](../CHANGELOG.md#134) 起提供。登录页移除常驻说明文字及信息展开／收起按钮，将空间留给 X 的登录内容；原生标题、操作区与网页区独立排布，WebView 使用有界且裁剪的剩余空间；首次加载和挂载前将原生宽高显式设为 `MATCH_PARENT`，并启用 `useWideViewPort` 与 `loadWithOverviewMode`，避免网页的动态视口高度被计算为零。主文档加载状态由 WebView 回调驱动，加载提示放在网页外部，不因 WebView 对象已创建而提前结束，也不代表 X 的异步登录步骤已完成。等待登录时仍占有当前工作流，取消后保留原链接，新的导入不能替换正在等待的任务。

取得媒体后，按原始媒体顺序选择最高质量 MP4，继续使用不携带账号 Cookie 的 CDN 请求，流式写入应用专属功能目录的临时文件。完成后通过共用 `FfmpegVideoEngine.probe` 校验视频流、尺寸和时长，再提交成品；网络层不负责视频解码。失败按视频报告，取消和失败清理未完成文件。协议、域名、重定向、响应大小与时间均受限制，远端地址不传给 FFmpeg。

链接解析保留 `/video/序号` 的原始媒体附件位置。多视频推文通过可挂起回调等待用户选择当前视频或全部视频；决策状态保存在 ViewModel，等待时不下载、不创建输出目录，取消仍保留输入链接。图片参与媒体位置编号，输出文件名则沿用原有视频序号。

成品交由原有用户存储层自动保存。结果页可将任一下载视频的应用专属 FileProvider URI 直接交给视频转 GIF 配置流程，使用原有参数、进度、取消和存储逻辑。返回配置页上一级时恢复原下载结果；源视频始终保留。接口支持范围与限制见 [下载推特视频](download_twitter_video.md)。

## 应用图标

项目根目录的 `natsuko.png` 是应用图标的唯一原图。启动器前景资源按 Android 密度生成 108/162/216/324/432 px 版本；普通启动器、圆形启动器、分享目标以及应用内品牌图标均引用这些同源资源。不单独维护另一套图标画面。

## 视频后端

FFmpeg 与 FFprobe 从官方源码构建，随 APK/AAB 内置，当前提供 `arm64-v8a` 和 `x86_64`。原生可执行文件以 `libnatsuko_ffmpeg.so`、`libnatsuko_ffprobe.so` 名称放在 `third_party/ffmpeg/jniLibs/<ABI>/`，由 Android 安装器解压到应用的 `nativeLibraryDir`，视频引擎从该只读安装目录启动进程。应用不会将可执行文件下载或复制到可写缓存后运行。

视频转 GIF 由 `VideoToGifProcessor` 通过 `ContentResolver` 将输入流式复制到本次任务的私有缓存目录，使 FFmpeg 能对包括分享导入在内的文档执行本地随机读取。共用引擎使用 FFprobe 探测视频流，再由 FFmpeg 完成采样、缩放、调色和 GIF 编码。调用使用独立进程参数，不通过 shell 拼接命令；协程取消会终止处理进程，引擎和功能处理器分别清理调色板、临时输入及未完成输出。

后续视频裁剪、转码、帧提取或其他处理能力应扩展共用引擎；不得另建 Android 系统媒体解码路径或运行时下载后端。启用组件与构建来源见 [FFmpeg 构建资料](../third_party/ffmpeg/README.md)。

## 性能与限制

- 图片解码使用 `ImageDecoder` 的软件位图和目标尺寸，单张默认限制最长边 4096 px。去除黑边为保留准确的像素边界，使用按图片方向解码的原始分辨率 sRGB 位图，不缩小输入；最长边超过 8192 px 或总像素超过 1600 万时逐文件报告失败。
- 去除黑边从四周向内检测完整的不透明黑色行或列，RGB 每通道均不超过 8；任意较亮或透明像素都会阻止该行或列被移除。无黑边和全黑图片保留完整范围并输出 PNG，结果页在文件名下方独立显示“未检测到可裁剪黑边（保持原尺寸）”；已裁剪的图片显示“已去除黑边”。不进行内容分割；与黑边同样完整且接近纯黑的边缘内容仍可能被裁去，详见 [去除黑边](crop_black_border.md)。
- 图片拼接配置页通过 `BitmapLoader` 在 IO 线程加载最长边 512 px 的完整预览，并保留正式处理使用的尺寸；与输出共用 `MergeLayout` 生成整体画布。按 URI 保存预览，排序时复用，替换输入、离开页面或取消加载时释放位图。
- 拼接结果限制最长边 8192 px、总像素 4000 万，按统一比例缩小并保持比例。
- PDF 按页、逐位图处理并及时回收；渲染输出最长边限制 4096 px。
- 图片调整不使用 `BitmapLoader` 的 4096 px 缩小策略：导出只解码成品覆盖的源区域，缩小时按成品分辨率的 2 倍解码，单个位图不超过 5200 万像素，解码区域与成品合计不超过 8000 万像素，WebP 每边不超过 16383 px。超限时报告原因并引导用户使用「缩小尺寸」，不会自动缩小。
- 视频转 GIF 第一遍从整段视频均匀采样最多 32 帧、每帧宽高均不超过 160 px 的代表画面，生成全局自适应调色板。输入调色板分析的像素样本最多为 32 × 160 × 160 = 819,200，限制颜色直方图增长。第二遍按用户配置的尺寸和采样计划编码最多 300 帧，并应用 Sierra 颜色抖动；两遍的采样计划和缩放尺寸分别计算。
- 两遍处理都需要解码源视频来取得样本，不缓存整段视频的已解码帧。调色板分析上限只约束颜色直方图，整体内存仍包括解码器参考帧、缩放及编码缓冲区，随源视频和输出尺寸变化。
- GIF 播放帧率与视频采样间隔独立，改变采样间隔会改变所选画面及输出总时长。采样后以毫秒时间基准重建播放时间，再写入 GIF 的百分之一秒帧延迟，避免较大采样间隔丢失播放时间精度；最后一帧显式保留按所选帧率计算的显示时间。GIF 最多支持 256 色，复杂照片或渐变仍受格式本身限制。
- 视频暂存会占用与输入文件大小相当的缓存空间；空间不足或 URI 读取失败会报告明确错误。容器、编码和配置文件的支持由内置 FFmpeg 构建决定。

应用不请求媒体库或全盘存储权限。默认用户目录使用 `MediaStore.Downloads`；自定义目录通过系统目录选择器取得持久读写授权。用户目录中的成品可独立于应用保留，应用专属副本会随卸载移除。


## 图片位置复制

`CopyLocationProcessor` 将已授权 URI 流式复制到工作文件，由 `LocationMetadataEngine` 使用内置 ExifTool/Perl 读写位置。来源先校验有效坐标；目标逐张处理，通过可挂起回调等待冲突决策，策略限定在单批次内。原文件不修改，结果复用 `OutputRepository` 和 `UserStorageRepository`。

Perl 可执行文件从安装器解压的 `nativeLibraryDir` 启动，受版本控制的 Perl 模块、ExifTool 模块和固定桥接脚本来自 APK assets。外部输入只作为参数和元数据处理，不执行 shell 命令；进程输出有长度限制，可取消并回收。重建资料见 `third_party/metadata/README.md`，交互说明见 [图片地理位置信息复制](copy_location.md)。

## 应用更新

设置页的「检查更新」由 `AppUpdateController` 驱动：检查 → 询问 → 下载 → 安装，每一步都由用户操作触发，不在后台联网。更新状态通过独立的 `StateFlow` 提供，不属于 `NatsukoUiState`，因此文件工作流重置时不会丢失；确认框与进度框显示在所有页面之上。下载和安装期间与处理、保存一样视为忙碌，拒绝新的导入；处理或保存进行中时不能开始更新。

`GitHubAppUpdater` 读取 GitHub 最新正式 Release，只向 GitHub 的 HTTPS 地址请求，下载后校验大小与 SHA-256，再由 `AppUpdateInstaller` 通过 `PackageInstaller` 会话交给系统覆盖安装；包名、版本号在安装前核对，签名由系统校验。应用不执行下载的文件。网络边界、安装包选择规则、权限与发布要求见 [应用更新](app_update.md)。
